Stack

top to bottom
01

IONOS VPS

Everything is hosted on an IONOS VPS. I originally looked at cobbling together a bunch of free offerings from various SaaS platforms, but IONOS turned out to be a great deal — forty-something bucks a month for a 16 GB VPS.

hosting
02

DuckLake (DuckDB + Postgres)

DuckDB is an amazing OLAP engine, but the single-writer / multiple-reader concurrency issue is kind of annoying — so I switched to the DuckLake architecture, using Postgres as the operational plane. Postgres is just the tried-and-true default for anything RDBMS, which is why I elected to go with it.

lakehouse
03

Dagster

For orchestration I just wanted to try something new — I had a little experience with Airflow and found it pretty bulky, just a lot going on. The Dagster UI is pretty neat and easy to understand. Some of the partitioning and backfill stuff is a little weird, but I think it would make sense at scale. Being able to run a read-only server alongside the admin server is nice too — pretty happy with it.

orchestration
04

dbt

I originally included dbt because you see it everywhere as the industry standard, but after starting another project and realizing I was basically recreating a lot of its functionality, I started appreciating it a lot more. The testing is awesome, being able to version-control your SQL is cool, and dbt docs generate is really neat — the lineage graphs and whatnot. Sometimes I do miss the first-class support ORMs offer, but, you know.

transformation
05

FastAPI

FastAPI is just my go-to. As a Python guy, spinning up quick things with a good spec given to Claude — FastAPI is great for that. What's serving right now, the person-graph API, isn't super complicated.

serving
06

React

For the front-facing apps, React is just my go-to. I'm not really concerned with learning another frontend framework at this point — it does what it needs to do for me. I'd like to do more D3.js stuff.

frontend
07

Metabase

Another piece of software I wanted to try out for the first time — a great open-source BI layer. It's actually one of the reasons I bumped the VPS from 8 GB up to 16 GB. Hopefully it'll make for some user-facing dashboards — exposing the data in more ways than just the APIs.

How it's built

01

CI/CD

Every push to main touching api/, web/, Caddyfile, or docker-compose.yml triggers a GitHub Actions build check, then an SSH deploy that runs docker compose up -d --build on the VPS — guarded so overlapping deploys can't race each other.

02

Containerized, single-origin deploy

Frontend and API ship as separate Docker images, but both sit behind one Caddy instance on a single domain — Caddy auto-provisions HTTPS and reverse-proxies /api/* to the backend, so the browser never crosses origins.

03

Tests & static checks

pytest plus Dagster asset checks and dbt schema tests cover the pipeline; ruff, mypy, and pre-commit keep the Python side honest; oxlint and tsc do the same for the React apps.

04

Config over code

Every API key and connection string — IMDb, TMDB, MotherDuck, and more — comes from environment variables, documented in .env.example and never committed.
